# Security Policy & Technical Architecture

## 1. Overview and Scope

**ElectroField** is an applied-electromagnetics workbench. The same Python engine (`engine/`) runs in one of two ways:

1. **In the browser (GitHub Pages):** there is no server. The `engine/*.py` files are loaded into [Pyodide](https://pyodide.org) (CPython compiled to WebAssembly, pinned v0.26.4 from jsDelivr) and called through `engine/routes.py` inside the browser sandbox.
2. **Locally:** `python run.py` starts a FastAPI server (`server/main.py`) bound to `127.0.0.1:8765` that serves the UI and the `/api/*` routes.

In both cases the engine receives only numeric or enumerated parameters; no user-supplied code or expressions are evaluated. The UI (`web/`) is static ES modules rendered with Plotly and KaTeX.

The old single-file WebGL workbench is kept in `legacy/` for reference only (sections 3.6–3.7).

## 3. Technical Security Controls & Threat Model

### 3.1. Input handling in the API
* All `/api/*` endpoints take numeric or enumerated parameters, validated by FastAPI/Pydantic types and by explicit range checks in each solver (`ValueError` → HTTP 400 with a plain-text message).
* There is no `eval`, `exec`, `new Function` or expression parser anywhere in the 3.x code path.
* Array sizes are fixed or clamped server-side (grids ≤ 161², sweeps ≤ 2000 points, ≤ 8 charges/wires) to bound CPU and memory.

### 3.2. Local-only server
* `run.py` binds to `127.0.0.1`; the API is not reachable from other machines unless the user changes the host deliberately.
* There are no accounts, cookies, sessions or database; the server holds no user state.

### 3.3. AI assistant (`server/assistant.py`)
* The assistant uses the official Anthropic SDK with the user's own credentials (`ANTHROPIC_API_KEY` or an `ant auth login` profile) read from the environment on the server side; the key is never sent to the browser or written to disk by ElectroField.
* The model can only call a fixed list of solver tools with JSON-schema-typed arguments; tool inputs go through the same validation as the API. It cannot run code, read files or reach other URLs.
* Model text is inserted into the page with `textContent` (no HTML injection); numbers shown to the user come from the engine, not the model.

### 3.4. EM tutor page (browser-side AI)
* The default "built-in tutor" runs entirely in the browser with no network request beyond the engine itself; it parses the question with fixed rules and calls only whitelisted engine routes.
* Optionally the user chooses a provider (Google Gemini, Groq, OpenRouter) and pastes their own free key. Requests go directly from the browser to that provider; ElectroField has no server in between and never receives the key.
* The key stays in memory unless the user ticks "remember", in which case it is kept in `localStorage` of that browser only.
* What is sent to the provider: the question, the last few turns, and the engine's numerical results.
* The model's plan is parsed as JSON and only whitelisted engine routes are executed, with the same parameter validation as the API. The answer is rendered as text nodes and KaTeX (no HTML injection), and every number in it is compared with the engine output.

### 3.5. Front-end rendering
* The UI builds DOM nodes with `document.createElement`/`textContent`; KaTeX renders only formula strings generated by the engine (`throwOnError: false`).
* Third-party code: on the local server Plotly is served from the installed `plotly` Python package; on GitHub Pages it is loaded from `cdn.jsdelivr.net`. KaTeX and Pyodide come from `cdn.jsdelivr.net`. All versions are pinned.
* Analytics: both `index.html` pages load GoatCounter (`gc.zgo.at`), which counts page views per chapter without cookies. Its script does not count visits from `localhost`/`127.0.0.1` by default.

### 3.6. Legacy WebGL page (`legacy/index.html`)
* Custom surface equations are filtered by `compileEquation()` (character-set restriction and identifier allow-list) before compilation; AI responses from the legacy external endpoint are escaped with `escapeHTML()` and their numbers coerced with `parseFloat()`.
* Mesh resolution and particle counts are capped to avoid GPU context loss.

### 3.7. Legacy desktop binary
* Built with PyInstaller from `legacy/ElectroField.spec`; it opens the local `index.html` via `file://` without opening network sockets.

## 4. Out of Scope

* **HTTP response headers on GitHub Pages** (CSP, X-Frame-Options, COOP): GitHub Pages does not let the site set them.
* **Exposing the local server to a network** by changing the bind address or running it behind a public proxy.
* **Client-side parameter tampering** in the browser — it only affects the local session.
* **Third-party CDN or API availability** (jsDelivr, GoatCounter, the AI providers used by the tutor, the Anthropic API for the optional assistant).

## 5. Reporting a Vulnerability

If you find a security issue (for example an XSS vector, a way to make the engine evaluate input as code, or a leak of a tutor API key), please report it privately rather than opening a public issue:

1. **GitHub Security Advisories:** Submit a report via the [**Security > Report a vulnerability**](https://github.com/atahanguney/ElectroField/security) tab in this repository.
2. **Direct Contact:** Reach out to the maintainer via GitHub or LinkedIn:
   * **Maintainer:** Atahan Güney (Department of Electrical & Electronics Engineering, Antalya Bilim University)
   * **GitHub:** [github.com/atahanguney](https://github.com/atahanguney)
   * **LinkedIn:** [linkedin.com/in/atahan-guney](https://www.linkedin.com/in/atahan-guney)

### What to Include in a Report
* A minimal proof-of-concept (PoC) input or request (e.g., the API call or assistant prompt that triggers the issue).
* The environment (browser and OS, or Python version for the local server).
* Expected behavior versus observed behavior.
